# 上游贡献与开发计划

## 术语表与命名约定

| 术语 | English / 缩写 | 本计划中的职责边界 | 不代表什么 |
|---|---|---|---|
| 上游仓库 | `tools-rs/ramag` | 接收经过独立验证、可单独审查的通用改进 | 不代表独立平台项目的代码来源或发布仓库 |
| 独立平台项目 | `bruceblink/ramag-platform` | 承载平台化、插件化和与上游方向不同的产品能力 | 不代表上游 PR 的依赖、同步目标或评审前置条件 |
| 上游基线 | `upstream/main` | 每个 PR 创建时使用的最新代码基线 | 不代表本地长期开发分支 |
| 贡献分支 | feature branch | 只承载一个可验收的上游变更 | 不代表独立平台的主线 |
| 用户可见功能 | user-facing feature | 必须经过运行时 UI 验收的界面或交互变更 | 不代表单元测试已经证明真实窗口行为 |

## 当前审查结论

本计划以 2026-09-06 刷新后的 `upstream/main`（`16e33a4`）为基线。上游当前是一个采用务实 Clean Architecture 的 GPUI 桌面工作台：`ramag-bin` 负责组合和启动，`ramag-ui` 提供 Shell、首页和 ActivityBar，各工具 crate 提供视图，`ramag-app` 编排用例，`ramag-domain` 定义实体与接口，`ramag-infra-*` 对接具体后端。

上游已经包含：

- 首页工具卡片拖拽排序、插入指示器、拖拽预览和顺序持久化；
- 数据库查询请求序号、取消、连接失效处理以及旧结果隔离；
- 数据库结果分页、排序、过滤、编辑、横向滚动和结果视图相关基础能力；
- 连接收藏、表导航收藏和多个工作台的响应式布局修复；
- MySQL、PostgreSQL、Redis、MongoDB、Git、SSH/SFTP、对象存储和可选剪贴板工作台。

因此，独立项目中的同名提交不能按提交标题直接移植。`ramag-platform` 相对上游有大量跨 crate 的数据库扩展、Kafka 完整工具、SQLite 支持、响应式 UI 修复和平台插件文档；其中很多内容已经被上游吸收，或依赖独立项目新增的架构与 crate，不能形成小范围上游 PR。

## 上游 PR 计划

### P0：主页工具 Pin

目标：在已有首页工具排序基础上增加独立的 Pin/取消 Pin 机制，形成可审查的用户功能。

范围：

- 工具注册表增加稳定的 Pin 状态或等价的首页布局状态；
- Pin 状态使用独立偏好键持久化，启动时读取并清理未知工具；
- 首页提供 Pinned 区域和全部工具区域；
- Pin/取消 Pin 操作不改变工具打开行为；
- Pinned 区域保留拖拽排序，全部工具区继续保持现有排序行为；
- 增加状态转换、偏好解析、未知工具清理和 GPUI 无头渲染测试。

边界：不引入插件 API、不修改数据库或 Kafka 架构、不复制 GitHub 的仓库卡片语义。

验收条件：

- 新用户、无效偏好、重复 ID 和工具被隐藏时均有确定结果；
- Pin 后重启仍保持状态，取消 Pin 后从 Pinned 区移除；
- 首页与 ActivityBar 不出现重复或错位工具；
- 至少完成 `ramag-ui` 目标测试、headless UI 交互/渲染检查；可用时补充 Windows 真实窗口截图验证；
- 通过 workspace fmt、Clippy、测试后才提交 PR。

### P1：现有工作台的独立稳定性修复

只从最新上游重新复现问题后选择条目，候选包括：

- 数据库查询或连接切换的竞态、旧结果回写和取消边界；
- 结果表格在窄窗口中的操作入口和滚动可用性；
- Git、SSH、对象存储工作台的状态切换和错误反馈；
- 现有工具排序与隐藏状态之间的持久化一致性。

每个问题单独建立最小复现、回归测试和单独 PR。若上游已包含对应修复则跳过，不为提交数量制造重复变更。

### P2：通用测试与维护改进

- 将能脱离独立平台架构的纯逻辑测试补回上游；
- 补充跨平台路径、空状态、错误状态和偏好迁移测试；
- 只提交能直接改善上游贡献流程的文档或 CI 改进。

## 不回馈上游的内容

- `ramag-platform` 的插件平台路线图、插件宿主、权限模型和外部插件协议；
- Kafka 工具及其基础设施的整套新增 crate；
- SQLite 作为新数据库引擎的完整实现；
- 数据库客户端的大规模 DataGrip 风格功能扩展；
- 依赖独立平台提交链、独立产品命名或独立发布流程的改动。

这些能力继续在 `bruceblink/ramag-platform` 独立开发；它们可以作为产品设计和工程实践的来源，但不作为上游 PR 的代码依赖。

## 每个 PR 的执行流程

```text
刷新 upstream/main
  -> 从 upstream/main 创建单功能分支
  -> 先写最小复现或回归测试
  -> 实现并检查变更边界
  -> 运行功能测试、fmt、Clippy、workspace 测试
  -> 用户可见功能执行真实窗口 UI 验收
  -> computer-use 不可用时使用截图和 headless 验收，并记录限制
  -> 提交一个 Conventional Commit
  -> 推送并创建 tools-rs/ramag PR
```

标准检查：

```powershell
git fetch upstream --prune
git switch -c <feature-branch> upstream/main
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

用户可见变更还必须记录实际启动平台、窗口尺寸、交互路径、截图/headless 证据和未验证的限制。未通过测试或 UI 验收的变更不得提交和推送。

## 独立平台项目开发线

独立平台项目不跟踪上游 PR 分支，也不要求把上游 PR 合并回独立项目。其开发顺序单独维护：

1. 平台 Core 与工具注册边界；
2. 插件 Manifest、设置命名空间与权限；
3. 内置工具迁移和生命周期管理；
4. 外部进程 IPC 插件宿主；
5. 稳定性、兼容性和插件开发者体验。

上游贡献和独立平台开发共享研究成果，但代码、分支、提交和发布目标保持分离。
